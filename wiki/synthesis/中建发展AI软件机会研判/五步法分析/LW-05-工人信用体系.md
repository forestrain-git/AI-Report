## 二、行业预判（六模块）

### M1 拆解行业

**产业链图**

```
数据源层                  平台层                    应用层                  终端用户
实名制考勤系统  ──→  云筑工匠(中建电商)    ──→  工人信用评分SaaS   ──→  总包单位HR/采购部
建安码/培训记录  ──→  建工一号/建筑港      ──→  班组信用评级      ──→  劳务公司
工资专户流水    ──→  劳查查/安心筑        ──→  金融风控输出      ──→  银行/保理公司
违章/事故记录   ──→  政府监管平台         ──→  用工合规报告      ──→  住建局/人社局
```

**利润分配**（100元收入拆解）

| 环节 | 毛利率 | 说明 |
|:---|:---:|:---|
| 数据采集与标准化 | 10-15% | 实名制数据分散在总包/分包/政府平台，清洗整合成本高 |
| 信用模型研发 | 60-70% | 算法团队是核心成本，模型训练后边际成本极低 |
| 产品化与交付 | 40-50% | SaaS模式边际成本低，但定制化需求（央企合规）拉低毛利 |
| 销售与获客 | 20-30% | ToB销售周期长，涉及合规审批决策链长 |
| 金融赋能（持牌合作） | 5-15% | 需与持牌征信机构分润，利润被压缩 |

**关键控制节点**：**数据资产型** — 云筑网拥有 1400 万+建筑工人的实名制数据（身份、工种、项目经历、考勤、工资支付记录），这是目前建筑行业规模最大的工人数据资产。竞品中最大的建筑港也仅有5600万数字档案但以招工为主，数据深度远不及云筑网。

**可优化环节**：建筑行业个人信用评价几乎空白（个人类信用信息仅占5.86%），用工决策长期依赖"熟人推荐"（达标率60%）和"包工头经验"，系统化信用评估是显著的效率洼地。

### M2 洞察变化

| 维度 | 变化 | 量级 | 证据 |
|:---|:---|:---:|:---|
| **政策法规** | 住建部2026年1号文——建成部-省-市-县四级信用信息归集体系 | 🔴大 | 住建部2026年1号文 |
| **政策法规** | 中办国办《关于健全社会信用体系的意见》——鼓励创新信用评价业务模式 | 🔴大 | 中办国办联合发文 |
| **政策法规** | 住建部建市〔2020〕105号+建办市函〔2025〕51号——拓展实名制系统、培育产业工人基地 | 🟡中 | 已在执行中 |
| **需求侧** | 行业"高薪却招不到人"结构性矛盾——月均收入5880元（六大行业最高）仍在流失 | 🔴大 | 四年流失1400万+，降幅25.2% |
| **需求侧** | 欠薪问题严重——2025年检察机关支持讨薪诉讼2.8万件，追索13.5亿元 | 🟡中 | 检察机关数据 |
| **新技术** | 替代数据征信技术成熟——深度学习模型评价工人"职业技能"和"个人稳定性" | 🟡中 | 已有学术验证 |
| **新技术** | 区块链存证+隐私计算——南京"芯连薪"、安心筑2500万份链上存证 | 🟡中 | 落地案例已验证 |

**判断**：这是一个**系统性变化** — 政策（四级信用体系归集+信用体系意见）+ 需求（工人流失+欠薪治理）+ 技术（替代数据征信+区块链存证）三重共振。但变化量级存在对冲因素：工人总量在持续萎缩（四年流失25%），市场基数在收缩，这是一个"蛋糕在缩小但切法在变"的机会。

### M3 预判稳态B

**原子级需求拆解**

| 用户 | 场景 | 解决什么问题 | 愿付多少钱 |
|:---|:---|:---|:---|
| 总包单位HR/项目经理 | 工人筛选与班组组建 | 熟人推荐达标率仅6%，网络招聘初试达标率仅6%，缺乏客观评价标准 | 50-200元/人次（按招聘成功付费）或3-10万/年（订阅） |
| 劳务公司 | 工人管理与信用背书 | 工人流动性高（3-8倍），无法预判工人稳定性 | 2-5万/年 |
| 金融机构（银行/保理） | 工人薪资贷/消费金融风控 | 建筑工人无央行征信记录，传统风控无法覆盖 | 按查询次数，0.5-2元/次 |
| 政府监管部门 | 用工合规监管与欠薪预警 | 工人信用信息碎片化，无法形成全貌 | 政府采购，50-200万/年 |

**稳态B推演**：

> （住建部四级信用体系归集政策落地）→（使得建筑工人信用数据从碎片化走向标准化、集中化）→（叠加工人流失加剧，用工方对"精准选人"需求急迫）→ **建筑行业用工决策从"熟人推荐+经验判断"转向"数据驱动的信用评价"，拥有最全数据的平台成为行业基础设施。**

**中建发展在稳态B中的位置**：数据资产层的核心持有者 — 1400万+工人的实名制数据（身份、考勤、工资、培训、违章）构成信用画像的数据底座。但需注意：数据所有权分散在各工程局和政府平台，云筑网是"汇聚者"而非"所有者"，数据确权是关键变量。

### M4 Timing

**周期定位**：**技术萌芽 → 早期探索的过渡期**

- 信用评价技术本身已成熟（替代数据征信、区块链存证），但建筑行业工人信用评价的产品化尚处极早期
- 竞品（建工一号、建筑港、劳查查）已在跑马圈地，但均未形成规模效应
- 住建部四级信用体系归集政策刚出台，市场标准尚未建立

**窗口期判断**：窗口已开，还有 **2-3 年**。原因：
- 住建部2026年1号文要求建成四级信用体系，各省将在2026-2028年密集落地
- 先行者有机会参与标准制定、占据数据入口
- 但征信牌照合规红线可能限制商业化速度

**太早风险**：中等 — 技术已成熟，但政策落地节奏不确定，各省执行力度差异大
**太晚风险**：中等 — 竞品已在布局，但尚无绝对领先者；市场标准未定，先行者劣势（需要承担教育成本）和先行者优势（参与标准制定）并存

### M5 天花板大小

**四方法交叉验证**

| 方法 | 估算 | 说明 |
|:---|:---|:---|
| **直接数据** | 建筑劳务管理数字化120亿元/年（仅中建体系测算） | 信用评价是劳务管理的子集，占比约15-20% → 18-24亿 |
| **Top-down** | 5115万从业人员 × 假设10%需信用评估 × 人均年价值50元 = 25.6亿 | 保守估算，不含金融场景 |
| **Bottom-up** | 云筑网1400万工人 × 假设5%活跃使用 × 年均100元 = 7000万 | 仅云筑网自身数据，极保守 |
| **类比法** | 个人征信市场约200亿（百行+朴道+央行征信中心）→ 建筑工人子市场约为其5-10% = 10-20亿 | 建筑工人是特殊群体，传统征信覆盖不到 |

**叠加金融场景天花板**：若工人信用数据成功输出至金融场景（薪资贷、消费金融），参考百行征信年收入约30亿，建筑工人信用市场的金融赋能部分可增加10-30亿。

**结论**：建筑工人信用评价可触达市场 **15-50亿元**，支撑数亿级体量公司。天花板受两个因素制约：（1）工人总量持续萎缩；（2）征信牌照合规路径限制金融场景变现速度。

### M6 集中度

**现状**：**极其分散，尚无头部玩家**
- 建工一号（50万+工人）、建筑港（5600万数字档案）、劳查查（10万+劳务队伍）均在早期
- 政府主导的信用平台（如宁波"甬薪精管"）区域性强，未形成全国网络
- 云筑网1400万工人数据量级远超竞品，但尚未独立推出信用评价产品

**趋势**：**C型（分散→集中）★ 最佳时机，但存在变数**
- 住建部四级信用体系归集政策将推动数据标准化和集中化
- 数据资产具有规模效应 — 数据越多，模型越准
- **变数**：征信牌照合规红线可能形成天然壁垒（只有持牌机构能做金融输出），导致市场分层——用工场景分散，金融场景集中

**匹配策略**：差异化深耕 — 利用1400万工人数据在"用工行为信用评价"做深做透，金融场景通过与持牌机构合作间接参与，而非自建征信平台。

**行业预判结论**：🟡 5 模块通过，1 模块（M5 天花板）存在收缩风险。工人总量持续萎缩是结构性制约，但政策窗口期和市场空白期仍构成中等机会。建议进入五步法项目分析，但需将"市场收缩风险"列为关键假设持续跟踪。

## 三、五步法逐层分析

### Step 1 需求

**目标用户**：总包单位HR/项目经理、劳务公司管理者（非"所有人"，是建筑行业用工决策者）

**场景与痛点**：

| 场景 | 痛点 | 刚性 |
|:---|:---|:---:|
| 工人招聘筛选 | 熟人推荐达标率60%，网络招聘初试达标率仅6%，缺乏客观评价标准，"用错人"成本极高 | 🟡中等 |
| 班组组建与调配 | 工人流动性3-8倍，跨项目调配无数据支撑，频繁换人导致工期延误 | 🟡中等 |
| 欠薪风险预警 | 2025年追索欠薪13.5亿元，工人无法预判雇主信用，企业无法预判劳务公司履约能力 | 🔴刚性 |
| 金融风控 | 建筑工人无央行征信记录，传统风控无法覆盖，薪资贷/消费金融审批难 | 🔴刚性 |

**替代方案**：

| 替代方案 | 优势 | 劣势 |
|:---|:---|:---|
| 熟人推荐 | 信任度高 | 达标率仅60%，范围窄，无法规模化 |
| 建工一号/建筑港 | 已有产品基础 | 数据量和深度远不及云筑网 |
| 央行征信 | 权威性高 | 建筑工人覆盖率极低，无工地行为数据 |
| 区块链存证平台（安心筑） | 数据可信 | 覆盖面有限（600+企业），侧重存证而非评价 |

**需求评估三角形**：
- 刚性：🟡 中等偏上 — 用工场景是"锦上添花"（有更好，没有也能用熟人推荐）；金融场景是"雪中送炭"（传统风控完全覆盖不到）
- 频次：🟡 中频 — 招工是阶段性需求（项目周期），金融场景是高频
- 普遍性：🔴 广泛 — 5000万+建筑工人都有信用评价需求

**关键假设**：
- H1（P0）：用工方（总包单位/劳务公司）愿意为"工人信用评价"付费，而不仅仅依赖熟人推荐
- H2（P1）：工人自身愿意参与信用体系（而非抵触被"打分"）

### Step 2 解决方案

**差异化定位**：

> 建工一号/建筑港是"招工平台+基础信用标签"，我们是"建筑行业工人全生命周期信用评价平台" — 区别在于：我们有 **1400万+工人的实名制行为数据**（考勤、工资、违章、培训、项目评价），能回答"这个工人在实际工地中的表现如何"，而竞品只能回答"这个工人有什么证书"或"这个工人在平台上填了什么信息"。

**核心卖点**：一句话 — **"证书告诉你能干什么，行为数据告诉你干得怎么样。"**

**产品内核（做了什么、不做什么）**：

| 做 ✅ | 不做 ❌ |
|:---|:---|
| 工人行为信用评分（基于考勤/工资/违章/培训/项目评价多维度） | 招工匹配平台（不做"滴滴式"派工，那是LW-02的方向） |
| 班组信用评级（聚合工人为班组维度） | 央行征信业务（不自建持牌征信机构） |
| 信用报告API输出（供金融机构调用） | C端信用查询App（不直接面向工人） |
| 欠薪风险预警（基于工资支付记录异常） | 全行业通用征信（专注建筑行业） |

**最小可用版本（MVP）**：
1. 基于云筑网1400万工人实名制数据，构建信用评分模型（考勤率+工资按时发放率+违章记录+培训完成率+项目评价）
2. 输出工人信用分（300-850分区间）和信用等级（A/B/C/D四档）
3. 在中建体系内1-2个工程局试点，嵌入工人入场审核流程
4. 验证信用分与实际用工表现的相关性

**关键假设**：
- H3（P0）：基于实名制行为数据的信用评分，能有效预测工人实际用工表现（出勤率、技能水平、稳定性）
- H4（P1）：信用评分模型在不同工种、不同地域之间具有泛化能力

### Step 3 商业模式

**单元模型选型**：**单客户（ToB SaaS）** — 按企业年订阅 + 按查询次数混合计费

**收入测算**：

| 收入来源 | 单价 | 客户基数（第3年） | 年收入 |
|:---|:---|:---|:---|
| 总包单位（标准版） | 5万/年 × 50家 | 中建系+其他央企+省级建工 | 250万 |
| 劳务公司（标准版） | 2万/年 × 200家 | 大中型劳务公司 | 400万 |
| 金融机构API调用 | 50万/年 × 3家 | 银行/保理公司（薪资贷场景） | 150万 |
| 政府监管平台 | 100万/年 × 2个 | 省级住建局（政府采购） | 200万 |
| **第3年合计** | | | **1000万** |

**成本结构**（第3年估算）：

| 成本项 | 金额 | 说明 |
|:---|:---|:---|
| 技术团队（算法+工程） | 500万 | 6-8人，含信用模型研发 |
| 外部数据对接 | 150万 | 政府平台/建安码数据接口开发 |
| 云服务/算力 | 100万 | 模型训练+推理 |
| 销售与获客 | 300万 | ToB销售团队3-4人 |
| 合规与法务 | 100万 | 征信合规审查、数据安全评估 |
| **总成本** | **1150万** | |
| **毛利** | **-150万** | **初期亏损** |

**LTV/CAC**：

| 指标 | 数值 | 判断 |
|:---|:---|:---|
| 年均客单价 | 4万（加权平均） | |
| 月均收入 | 0.33万 | |
| 月流失率 | 5%（信用评价非刚需高频，流失偏高） | ⚠️ 偏高 |
| LTV | 0.33万/5% = 6.6万 | |
| CAC | 3万（ToB销售） | |
| **LTV/CAC** | **2.2** | ⚠️ 偏低（<3，需优化留存） |
| 回收期 | 3万/0.33万 = 9个月 | ⚠️ 偏长 |

**关键假设**：
- H5（P1）：第3年能获取50家总包单位客户
- H6（P0）：金融场景API收入在合规路径打通后能贡献主要利润（当前受牌照限制）
- H7（P2）：月流失率可从5%降至3%（通过深度嵌入用工流程提升粘性）

### Step 4 增长

**获客渠道清单**（优先级排序）：

| 优先级 | 渠道 | 预估CAC | 说明 |
|:---:|:---|:---:|:---|
| 1 | **中建体系内复制** | 0（内部推广） | 8个工程局 + N个子公司，已有实名制基础 |
| 2 | **云筑网现有客户转化** | 1-2万 | 云筑工匠已覆盖的总包单位和劳务公司 |
| 3 | **政府渠道（住建局）** | 5-10万 | 借四级信用体系归集政策，对接省级住建局 |
| 4 | **金融机构联合推广** | 3-5万 | 与持牌征信机构合作，联合推广薪资贷场景 |
| 5 | **行业协会** | 3-5万 | 中国建筑业协会、各地建筑劳务协会 |

**增长引擎**：**黏着式** — 信用评价一旦嵌入场审核心流程，切换成本高（历史信用数据迁移难）。但黏性强度弱于供应商风控（LW-01），因为用工场景频次低于采购场景。

**增长阶段**：

| 阶段 | 核心任务 | 关键指标 | 时间 |
|:---|:---|:---|:---|

**壁垒类型**：

| 壁垒类型 | 具体内容 | 强度 |
|:---|:---|:---:|

| **网络效应** | 弱 — 工人信用评价是B2B工具，不直接产生网络效应 | 🔴弱 |

**可复制性评估**：
- 建工一号/建筑港复制：**2-3年** — 他们已有基础数据，但规模远小于云筑网（50万 vs 1400万）
- 其他建筑央企复制：**2-3年** — 中铁/中交等有自有平台数据，但整合难度大
- 新进入者复制：**极难** — 需要同时具备行业数据+实名制系统接入+政策资质
- **最大威胁**：住建部主导的政府统一信用平台 — 如果政府自建全国性平台，所有商业平台都将被边缘化

**关键假设**：
- H10（P0）：政府信用体系是"归集+标准"而非"自建+垄断"，留给商业平台空间
- H11（P1）：1400万工人数据在法律上可以用于信用评价产品对外输出

## 七、备选路径

**Plan A（首选）**：建筑行业工人全生命周期信用评价SaaS
- 路径：中建体系内验证 → 总包/劳务公司覆盖 → 金融场景API（与持牌机构合作） → 政府平台对接
- 目标：第3年收入1000万，第5年收入5000万+

**Plan B（备选）**：信用数据基础设施服务商（不做终端产品，只做数据和模型输出）
- 路径：将工人信用评分模型封装为API，输出给持牌征信机构、金融机构、政府平台
- 优势：规避征信牌照风险，更轻资产，专注数据和算法
- 目标：第3年3-5家机构合作，API收入300万/年

**Plan C（退出条件）**：
- 验证期内（6个月）中建体系内≥3个工程局拒绝接入 → 内部需求不成立
- 法律合规审查结论为数据不可对外输出且金融场景无法合作 → 市场天花板大幅缩小
- 信用评分AUC<0.75 → 模型预测能力不足以支撑付费
- 政府主导建设全国性统一工人信用平台，商业空间被压缩 → 及时转向

## 八、与LW-01（工人技能画像）的协同关系

工人信用体系（LW-05）与工人技能画像（LW-01）是**天然的上下游关系**：

```
LW-01 工人技能画像（数据层）
  │
  ├── 工种标签、技能认证、培训记录
  ├── 项目经历、考核数据
  └── 人岗匹配模型
  │
  ▼
LW-05 工人信用体系（评价层）
  │
  ├── 技能维度 → 信用评分的"能力"因子
  ├── 行为维度 → 信用评分的"稳定性"因子（考勤/违章/工资）
  └── 综合信用输出 → 用工决策/金融风控
```

**建议**：LW-01和LW-05应作为"组合拳"推进 — LW-01构建工人数据底座和技能标签，LW-05在此基础上叠加行为数据形成信用评价。两者共享同一套实名制数据资产，边际成本极低。LW-01的"人岗匹配"功能可作为LW-05的增值服务（"不仅能告诉你这个工人靠不靠谱，还能告诉你适不适合这个岗位"）。

## 九、建议下一步行动（最小验证）

**第一件事（本周）**：在中建体系内选择 1 个工程局的劳务管理部门，用云筑网实名制数据构建一个"原型信用评分"，与该局HR的人工评价做对比

- **验证目标**：行为数据信用评分与HR人工评价的相关系数≥0.7
- **实验设计**：
  1. 选取该局近1年的500名已入场工人（含100名已离场/被清退工人）
  2. 基于考勤率、工资按时发放记录、违章次数、培训完成率、项目评价5个维度构建信用评分
  3. 将评分结果与该局HR的人工评价（好/中/差三档）做对比
  4. 重点验证：高分组和低分组在实际用工表现（出勤率、事故率、离职率）上是否有显著差异
- **成本预算**：3周时间 + 1名算法工程师 + 0元外部采购（数据已有）
- **成功标准**：信用分与HR评价的相关系数≥0.7；高分组（前20%）出勤率≥90%，低分组（后20%）出勤率≤75%
